# refactor: Replace Tailwind standalone binary with @tailwindcss/cli via npm

## Overview

Replace the manually downloaded Tailwind v4 standalone binary with `@tailwindcss/cli` installed as an npm devDependency. The build invocation changes from `./tailwindcss` to `npx @tailwindcss/cli`. CI drops the curl/cache binary steps and uses a standard `npm ci` install instead. The `wrangler-action@v3` deploy step is unchanged.

## Problem Frame

The current setup requires manually downloading a platform-specific binary, gitignoring it, and managing its version via a workflow env var + `actions/cache`. This is non-standard and error-prone — the binary isn't checked in, the download URL must stay in sync with the version, and local setup requires extra curl steps. Using `@tailwindcss/cli` as a standard npm devDependency is simpler, more conventional, and removes the binary management entirely. The underlying Tailwind binary is identical — `@tailwindcss/cli` is a native binary distributed via npm, not a JS runtime wrapper.

## Requirements Trace

- R1. `npm run build` invokes Tailwind via `@tailwindcss/cli`, produces `dist/` correctly.
- R2. CI workflow builds and deploys on push to `main` without downloading a standalone binary.
- R3. Local dev setup requires only `npm install` — no manual binary download steps.
- R4. The `.gitignore` entry for the `tailwindcss` binary is removed.
- R5. README reflects the new setup process.

## Scope Boundaries

- No changes to `src/input.css`, `src/index.html`, or any visual output.
- No changes to `wrangler.toml`, `wrangler-action@v3` deploy step, or CF Workers config.
- No Tailwind version bump — stays at v4.2.2 (or latest v4 patch; pin same major.minor).
- No changes to `scripts/build.sh` logic — only the Tailwind invocation line and binary-detection preamble change.

## Key Technical Decisions

- **`@tailwindcss/cli` not `tailwindcss`:** In Tailwind v4 the CLI was split into a separate package `@tailwindcss/cli`. The main `tailwindcss` package no longer exposes a CLI binary. The invocation becomes `npx @tailwindcss/cli` or `./node_modules/.bin/tailwindcss` (the binary installed by `@tailwindcss/cli` is named `tailwindcss`).
- **`npm ci` in CI, not `npm install`:** The workflow should use `npm ci` for reproducible installs from a lockfile. A `package-lock.json` must be committed.
- **`scripts/build.sh` simplified:** The binary-detection preamble (lines 7–18) is no longer needed. The script invokes `npx @tailwindcss/cli` directly. The `TAILWIND_BIN` env var fallback is removed.
- **`wrangler-action@v3` unchanged:** It manages its own Node/npm environment internally. The `npm ci` step before it installs devDependencies (including wrangler) so the action's `wrangler` is also available if needed, but the action itself remains the deploy mechanism.

## Open Questions

### Resolved During Planning

- **Should wrangler also move to npm?** Yes — it's already a devDependency in `package.json`. `npm ci` installs it, so it's available in the workflow shell. `wrangler-action@v3` can still be used for deploy (it handles auth cleanly); no reason to change it.
- **Pin exact version or range?** Pin `@tailwindcss/cli` at `4.2.2` to match the current standalone binary version, consistent with existing pinning approach.
- **`package-lock.json` committed?** Yes — required for `npm ci` in CI. Currently deleted from the repo (it was the old Nuxt lockfile). A fresh one is generated by `npm install` locally and committed.

### Deferred to Implementation

- Whether to invoke via `npx @tailwindcss/cli` or `./node_modules/.bin/tailwindcss` in the build script — both work; implementer picks whichever reads more clearly.

## System-Wide Impact

- **Interaction graph:** No callbacks or middleware. The only affected surfaces are the local build command and the CI workflow.
- **Error propagation:** Build failures surface the same way — in the terminal locally, in GitHub Actions logs in CI.
- **State lifecycle risks:** None. The `package-lock.json` must be committed before CI can use `npm ci`; if it's absent, CI will fall back to `npm install` (with a warning) or fail depending on npm version. Commit order matters: Unit 1 must land before Unit 3 is merged.
- **API surface parity:** None.
- **Unchanged invariants:** `dist/` output is identical — same Tailwind v4.2.2 binary, same `src/input.css` input, same flags. Visual output is unaffected.

## Risks & Dependencies

| Risk | Mitigation |
|------|------------|
| `package-lock.json` missing when CI runs Unit 3 changes | Units 1 and 3 must be committed together or Unit 1 must land first. A single atomic commit covering all four units eliminates this. |
| `@tailwindcss/cli` package name differs from the binary name `tailwindcss` | Confirmed: `@tailwindcss/cli` installs a binary named `tailwindcss` at `node_modules/.bin/tailwindcss`. `npx @tailwindcss/cli` also resolves correctly. No ambiguity at runtime. |
| Old standalone binary still present locally after the change | The `tailwindcss` binary will no longer be gitignored after Unit 4. Run `rm tailwindcss` locally after the change to avoid confusion. |
